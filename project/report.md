Проект — REST-сервис, который по анкете заявителя предсказывает вероятность дефолта по кредиту и возвращает решение `approve`/`reject` относительно настраиваемого порога. Под капотом — выбор лучшей из двух моделей (Logistic Regression vs LightGBM) по ROC-AUC на отложенной валидации.

---

## 2. Постановка задачи и контекст

**Предметная область.** Кредитный скоринг физических лиц. Пользователь сервиса — кредитный аналитик / антифрод-инженер банка. Сценарий: на вход поступает заявка (анкета, финансы, прошлые контакты с бюро), на выход — оценка риска и рекомендация.

**Формулировка в терминах ML.**

- Тип задачи: бинарная классификация.
- Вход: ~23 признака заявки (14 числовых, 9 категориальных) из основной таблицы датасета Home Credit Default Risk.
- Выход: вероятность класса `TARGET = 1` (серьёзная просрочка платежа).
- Требования: интерпретируемость (банковский сценарий), устойчивость к пропускам (`EXT_SOURCE_1` и `OCCUPATION_TYPE` содержат много NaN), скорость инференса (<50 мс).

**Целевые метрики.**

- **ROC-AUC** — главная, как в оригинальном соревновании Kaggle, не зависит от threshold.
- **PR-AUC** — устойчивее ROC-AUC при сильном дисбалансе классов (~6-8% положительных).
- **KS-статистика** — классическая метрика разделения в скоринге.
- **F1 @ threshold** — для дополнительного контроля при фиксированном пороге.
- **log-loss / Brier** — для калибровки вероятностей.

## 3. Данные

### Источник

[Home Credit Default Risk на Kaggle](https://www.kaggle.com/c/home-credit-default-risk/data). Используется только `application_train.csv` — основная таблица заявок (~300 тыс. строк, ~120 колонок), без вспомогательных таблиц (`bureau`, `previous_application`, `installments_payments` и т.п.).

В репозитории сам CSV не лежит. Если файла нет, пайплайн автоматически генерирует **синтетический Home Credit-подобный датасет** в `src/data/synthetic.py` с той же схемой и реалистичными распределениями. Цель — позволить запустить проект «из коробки», не требуя аккаунта Kaggle и не нарушая лицензию датасета.

### Структура подмножества, на котором обучаемся

| Тип            | Колонки                                                                                                                                                                                         |
|----------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Числовые (14)  | AMT_INCOME_TOTAL, AMT_CREDIT, AMT_ANNUITY, AMT_GOODS_PRICE, DAYS_BIRTH, DAYS_EMPLOYED, DAYS_REGISTRATION, DAYS_ID_PUBLISH, CNT_CHILDREN, CNT_FAM_MEMBERS, REGION_POPULATION_RELATIVE, EXT_SOURCE_1/2/3 |
| Категориальные (9) | NAME_CONTRACT_TYPE, CODE_GENDER, FLAG_OWN_CAR, FLAG_OWN_REALTY, NAME_INCOME_TYPE, NAME_EDUCATION_TYPE, NAME_FAMILY_STATUS, NAME_HOUSING_TYPE, OCCUPATION_TYPE                                       |
| Target         | TARGET ∈ {0, 1}                                                                                                                                                                                  |

### Предобработка и EDA

Подробно — в `notebooks/01_eda.ipynb`. Основные наблюдения:

1. **Несбалансированные классы**, ~6-8% положительных. Влияет на выбор метрик (ROC-AUC, PR-AUC) и обучение (`class_weight='balanced'`).
2. **Пропуски в EXT_SOURCE_1** (~55%), **EXT_SOURCE_3** (~20%), **OCCUPATION_TYPE** (~30%). Это особенность реального датасета, воспроизведена в синтетике.
3. **Сентинел `DAYS_EMPLOYED = 365243`** для пенсионеров заменяется на NaN на этапе `_clean()`.
4. **EXT_SOURCE_1/2/3** — самые сильные одиночные предикторы. KDE по классам различается визуально, корреляции с TARGET по абсолютной величине — выше остальных признаков.
5. Возраст (через DAYS_BIRTH) и стаж (DAYS_EMPLOYED) — стандартные скоринг-факторы, корреляция с TARGET отрицательная (старше + дольше работает → ниже риск).

Препроцессинг — sklearn `ColumnTransformer` (`src/data/preprocessing.py` для baseline, отдельный для LightGBM):

- numeric: `SimpleImputer(median)` + `StandardScaler` (для LogReg). Для LightGBM не масштабируем (не нужно).
- categorical: `SimpleImputer(most_frequent)` + `OneHotEncoder(handle_unknown='ignore', min_frequency=20)`.

## 4. Модели и подходы

### Baseline — Logistic Regression

`src/models/baseline.py`. Параметры: `C=1.0`, `max_iter=1000`, `class_weight='balanced'`, `solver='lbfgs'`. Логистическая регрессия — стандартная стартовая точка в скоринге, интерпретируема, дешёва.

### Улучшенная модель — LightGBM

`src/models/improved.py`. LGBMClassifier:

- `n_estimators=400`, `learning_rate=0.05`
- `num_leaves=31`, `min_child_samples=50`
- `reg_alpha=0.1`, `reg_lambda=0.1`
- `class_weight='balanced'`

Выбран ровно за то, что обычно даёт LightGBM/CatBoost преимущество в табличной задаче: native missing handling, нелинейные взаимодействия, устойчивость к шуму.

Гиперпараметры — близкие к разумным умолчаниям, без полного тюнинга по сетке (это вынесено в «Дальнейшую работу», чтобы сохранить честность отчёта).

## 5. Экспериментальный протокол и результаты

### Протокол

- Стратифицированный сплит train/val/test = 70/10/20 от исходного датасета. Соотношение классов в каждом фолде сохраняется.
- Финальная модель выбирается по **ROC-AUC на val**, чтобы не «подсматривать» в test.
- На test считаются итоговые метрики (без подмены порога).

### Результаты на реальном Home Credit (307 511 строк, positive rate 8.07%)

| Модель              | ROC-AUC (val) | PR-AUC (val) | KS (val) | F1 @ 0.5 (val) | log-loss (val) |
|---------------------|--------------:|-------------:|---------:|---------------:|---------------:|
| Logistic Regression | 0.7355        | 0.2035       | 0.3492   | 0.2510         | 0.604          |
| LightGBM            | **0.7496**    | **0.2317**   | **0.3651** | **0.2652**   | **0.556**      |

Финальная модель — **LightGBM** — на отложенном **test (61 503 строки)**:

| Метрика  | Значение |
|----------|---------:|
| ROC-AUC  | 0.7580   |
| PR-AUC   | 0.2476   |
| KS       | 0.3826   |
| F1 @ 0.5 | 0.2726   |
| log-loss | 0.5487   |
| Brier    | 0.1853   |

Точные числа — в `artifacts/model.metrics.json`.

### Обсуждение

LightGBM обыгрывает LogReg на всех метриках — это согласуется с публичными результатами по Home Credit. Прирост ROC-AUC ~1.4 пункта (0.7496 vs 0.7355) не выглядит большим, но:

- **PR-AUC** растёт сильнее (с 0.20 до 0.23, +14% относительно) — это важнее ROC-AUC при сильном дисбалансе;
- **log-loss** падает заметно (0.604 → 0.556) — LightGBM лучше калиброван и не «штрафуется» так за уверенные ошибки;
- LightGBM умеет работать с пропусками натив­но (особенно важно для EXT_SOURCE_1, ~55% NaN), нелинейности и взаимодействия (отношение credit/income, эффект возраста для разных типов занятости).

Дальнейший рост качества (до публичных ~0.78-0.79 ROC-AUC) даёт feature engineering из вспомогательных таблиц `bureau.csv` и `previous_application.csv` — это вынесено в «Дальнейшую работу».

Метрики на test близки к val (ROC-AUC 0.758 vs 0.750) — переобучения нет, обобщаемость подтверждена.

### Выбор финальной модели

Финальной выбирается модель с большей **val ROC-AUC** (`src/models/train.py:90-100`). На реальных данных Home Credit это **LightGBM** (0.7496 vs 0.7355). Артефакт сохраняется единым joblib-бандлом и подгружается сервисом без дополнительных условий — название модели приходит вместе с ответом сервиса (`model_name: "improved (lightgbm)"`).

Trade-offs, которые учитывали:

- **LogReg:** дешевле, интерпретируемая, легко калибруется → лучше для отчётности, регуляторики;
- **LightGBM:** выше качество на реальных данных, native missing handling → лучше для продакшн-инференса при наличии «грязного» входа.

## 6. Архитектура решения и сервис

### Пайплайн

```
                       ┌──────────────────────┐
                       │ configs/model.yaml   │
                       └──────────┬───────────┘
                                  │
   data/raw/application_train.csv │
   (or generated synthetic CSV)   │
              │                   ▼
              ▼          src.utils.config.TrainConfig
   src.data.dataset.load_dataset ──► split (train/val/test)
              │
              ▼
   ┌──────────────────────┐    ┌─────────────────────────┐
   │ baseline pipeline    │    │ improved pipeline       │
   │ (LogReg)             │    │ (LightGBM)              │
   └──────────┬───────────┘    └────────────┬────────────┘
              │ fit + score                 │
              └─────────────┬───────────────┘
                            ▼
                   pick best by val ROC-AUC
                            │
                            ▼
              artifacts/model.joblib  (pipeline + meta)
                            │
                            ▼
                src.service.predictor.Predictor
                            │
                            ▼
                  FastAPI: /predict, /health
```

Один и тот же sklearn-пайплайн обучается на этапе train.py и сериализуется целиком (joblib). Сервис не повторяет препроцессинг отдельно — он лежит внутри `Pipeline`. Это устраняет классический рассинхрон «train preprocessing != serving preprocessing».

### API

| Method | Path             | Описание                                          |
|--------|------------------|---------------------------------------------------|
| GET    | `/health`        | Статус: модель загружена, имя, время обучения.    |
| POST   | `/predict`       | Скоринг одной заявки → вероятность + решение.     |
| POST   | `/predict/batch` | Скоринг массива заявок.                           |
| GET    | `/`              | Краткая информация и ссылки.                      |
| GET    | `/docs`          | Swagger UI.                                       |

Pydantic-схемы валидируют входные данные (см. `src/service/schemas.py`): неотрицательные суммы, диапазоны `EXT_SOURCE_* ∈ [0, 1]` и т.п.

### Стек

- ML: scikit-learn, lightgbm.
- Сервис: FastAPI + uvicorn, pydantic v2, pydantic-settings.
- Конфиги: YAML (training) + `.env` (service).
- Тесты: pytest + httpx (`fastapi.testclient`).
- Контейнеризация: Dockerfile (`python:3.11-slim` + libgomp1) + docker-compose с healthcheck.

## 7. Наблюдаемость, конфигурация, безопасность

**Логи.** Все запросы пишутся через middleware с request_id, методом, путём, статусом и длительностью (`src/service/app.py:50-65`). Формат — однострочный, легко парсится. Также логируются загрузка модели и обучение.

**Health-check.** `GET /health` возвращает `model_loaded`, имя модели и время обучения. Используется в `docker-compose.yml`.

**Конфигурация.** Параметры обучения вынесены в `configs/model.yaml` (фичи, гиперпараметры моделей, размеры сплитов, синтетика on/off). Параметры сервиса — через `pydantic-settings` (env / `.env`): хост, порт, путь к модели, threshold решения, log level.

**Безопасность.**

- В репозитории нет `.env`, ключей, токенов, реальных CSV. Всё это под `.gitignore`/`.dockerignore`.
- Пример конфигурации лежит в `configs/env.example`.
- В образ Docker `data/raw/` не попадает (`.dockerignore`); только обученный артефакт и код.

## 8. Ограничения и дальнейшая работа

Текущие ограничения:

- По умолчанию обучаемся на синтетике — метрики реалистичны по форме, но не сопоставимы с реальным датасетом.
- Используется только `application_train.csv`. Без агрегатов из `bureau.csv` / `previous_application.csv` качество ограничено.
- Гиперпараметры взяты разумными умолчаниями без полного грид-сёрча / Optuna.
- Нет калибровки вероятностей (`CalibratedClassifierCV`) — для бизнес-решений это полезно.
- Нет SHAP-эндпоинта в сервисе (есть только LightGBM feature importance в ноутбуке).
- Нет MLflow / DVC — версионирование артефакта только по имени файла + meta внутри bundle.

Что хотелось бы добавить:

- feature engineering из дополнительных таблиц Home Credit;
- Optuna-тюнинг + early stopping по val;
- `/predict/explain` с SHAP top-K факторов;
- калибровка + threshold tuning под асимметричную бизнес-стоимость FP/FN;
- Prometheus-метрики и Grafana-дашборд (latency, RPS, distribution drift).

## 9. Сценарий демонстрации на защите

1. Показать структуру: `src/`, `notebooks/`, `configs/`, `tests/`.
2. Запустить `python -m src.models.train` (или показать готовый `artifacts/model.metrics.json`).
3. Запустить `python -m src.service`, открыть `http://127.0.0.1:8000/docs`.
4. Сделать 2 запроса к `/predict`: «хороший» клиент (высокие EXT_SOURCE, высокий доход) и «плохой» (низкие EXT_SOURCE, большой кредит на маленький доход). Прокомментировать вероятности.
5. Прогнать `pytest tests -v` — все 10 тестов проходят.
6. Открыть `notebooks/02_models_comparison.ipynb`: показать таблицу метрик и ROC/PR кривые.

На что обратить внимание:

- единый sklearn-пайплайн обучается и сериализуется целиком — нет «train/serve skew»;
- решение `approve/reject` управляется порогом из конфига, а не зашито в код;
- сервис устойчив к частично заполненным заявкам (любое поле опционально);
- проект полностью воспроизводим без аккаунта Kaggle благодаря синтетическому генератору.
