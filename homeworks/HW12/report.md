# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использовался датасет `S12-hw-dataset.csv` — часовой временной ряд (4320 наблюдений, 180 дней). Прогнозировалось следующее значение `target`.
- Данные разбиты по времени: **train** (70%) / **validation** (15%) / **test** (15%).
- Сравнивались 4 подхода: B1 (naive-last), B2 (moving-average 24h), B3 (Ridge на лаговых/rolling/календарных признаках), R1 (GRU на оконном представлении).
- Лучшим оказался **B3 (Ridge)** — наименьший MAE на validation (4.89). Ridge эффективно комбинирует лаговые и календарные признаки без сложной архитектуры.

## 2. Среда и воспроизводимость

- **torch:** 2.8.0
- **Устройство (CPU/GPU):** CPU

## 3. Данные и постановка задачи

- **Датасет:** S12-hw-dataset.csv
- **Целевая колонка:** `target`
- **Частота временного ряда:** 1 час (hourly)
- **Горизонт прогноза:** 1 шаг (следующий час)
- **Размер датасета:** 4320 наблюдений
- **Диапазон дат:** 2025-01-01 00:00 — 2025-06-29 23:00
- **Есть ли дополнительные внешние признаки:** нет, только `date` и `target`

**Комментарий:** Ряд демонстрирует слабый положительный тренд (среднее значение растёт к лету). Наблюдается выраженная суточная сезонность (24-часовой цикл). Явных выбросов нет, пропуски отсутствуют. Ряд нестационарен из-за тренда, что усложняет прогноз для простых baseline-моделей.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- **Как выполнен split:** хронологически, без перемешивания — первые 70% данных в train, следующие 15% в validation, последние 15% в test.
- **Доли / интервалы:** Train: 3024 (2025-01-01 — 2025-05-06), Val: 648 (2025-05-06 — 2025-06-02), Test: 648 (2025-06-02 — 2025-06-29).
- **Почему random split некорректен:** наблюдения во временном ряде автокоррелированы. При случайном разбиении будущие значения попадают в train, создавая утечку данных (data leakage). Модель фактически «видит» будущее при обучении, что завышает метрики и делает оценку качества неадекватной.

### 4.2. Признаки для baseline-моделей

- **Лаги:** lag_1, lag_7, lag_14, lag_24, lag_168 (неделя)
- **Rolling-признаки:** rolling_mean_7, rolling_std_7, rolling_mean_24 — все вычислены со сдвигом `shift(1)` для предотвращения утечки
- **Календарные признаки:** hour, dayofweek, month, is_weekend
- **Обработка пропусков после лагов/rolling:** первые 168 строк train с NaN удалены (из-за lag_168); в val и test пропусков нет
- **Масштабирование:** StandardScaler, обучен только на train (`fit_transform` на train, `transform` на val/test)

## 5. Модели и эксперименты (B1, B2, B3, R1)

- **B1 (naive-last):** прогноз = предыдущее значение (lag_1). Без обучения.
- **B2 (moving-average):** прогноз = скользящее среднее за последние 24 часа. Без обучения.
- **B3 (ridge-lag-features):** Ridge(alpha=1.0) на 12 признаках (лаги + rolling + календарь). Масштабирование StandardScaler.
- **R1 (gru-forecast):** GRU(hidden=64, layers=1) на оконном представлении (window=48). MSELoss, Adam, early stopping.

**Дополнительно:**
- **Основная метрика выбора лучшей модели:** val MAE
- **Дополнительные метрики:** RMSE, MAPE
- **window_size для GRU:** 48
- **Batch size:** 64
- **Максимальное число эпох:** 50
- **Optimizer:** Adam
- **Learning rate:** 0.001
- **Как сохранялась лучшая модель:** по минимальному val MAE, state_dict сохранён в `best_gru.pt`

## 7. Анализ

Наивный baseline B1 (naive-last) показал MAE 6.44 — неплохой результат для часового ряда, что объясняется высокой автокорреляцией соседних значений. Тем не менее, B1 не способен учитывать суточные паттерны и тренд.

Moving average (B2) оказался самым слабым подходом (MAE 13.40), поскольку 24-часовое среднее сильно сглаживает ряд и не успевает за быстрыми колебаниями. Усреднение по суткам «отстаёт» от реальных значений.

Ridge на признаках (B3) показал лучший результат (MAE 4.89), эффективно комбинируя lag_1 (краткосрочная динамика), lag_24/lag_168 (суточный и недельный паттерны) и календарные признаки. Линейная модель хорошо справляется, когда признаки корректно отражают структуру ряда.

GRU (R1) показала MAE 5.06 — немного хуже Ridge. Это может объясняться тем, что GRU работает только с одномерным входом (значения target), тогда как Ridge использует обширный набор инженерных признаков. Для часового ряда с выраженными паттернами ручные признаки оказались информативнее автоматического обучения представлений.

Ряд имеет слабый тренд и выраженную суточную сезонность. Это хорошо улавливается лагами lag_24 и lag_168, что объясняет успех B3.

Возможные утечки данных: (1) rolling/lag без shift — мы использовали shift(1); (2) scaler на всём датасете — мы обучали только на train; (3) random split — мы использовали temporal split.

Выбор лучшей модели по validation, а не по test, принципиален: test должен имитировать реальную эксплуатацию, где модель видит данные впервые. Оптимизация по test привела бы к переобучению на конкретном участке.

Наиболее показательные ошибки модели возникают в местах резких скачков ряда, где ни лаги, ни rolling-средние не способны предсказать внезапное изменение.

## 8. Итоговый вывод

Для данной задачи прогноза часового временного ряда на один шаг вперёд базовый подход — Ridge на лаговых, rolling- и календарных признаках — оказался лучшим. Его MAE (4.89 на val, 4.48 на test) ниже, чем у GRU, при значительно меньших вычислительных затратах.

Простой baseline на признаках достаточен, когда ряд имеет регулярные паттерны (суточность, недельность) и задача ограничена одношаговым прогнозом. Переходить к GRU и другим нейросетям имеет смысл при многошаговом прогнозе, многомерных рядах или когда ручной feature engineering затруднён.

Главный вывод про валидацию: для временных рядов обязателен temporal split, а все признаки и масштабирования должны строиться без утечки информации из будущего. Random split создаёт иллюзию качества, которая не воспроизводится в продакшене.
