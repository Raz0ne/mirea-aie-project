# HW14 – эмбеддинги, FAISS, оценка retrieval и mini-RAG по базе знаний

## 1. Кратко: что сделано

- Использована собственная текстовая база знаний — справочник по Python (20 документов). Выбрана потому, что документы тематически разнообразны, но относятся к одной предметной области, что позволяет формулировать конкретные запросы с ожидаемыми ответами.
- Чанкинг выполнен фиксированным разбиением по символам с перекрытием (chunk_size=200, overlap=50), получено 83 чанка.
- Для векторизации использован TF-IDF + TruncatedSVD (dim=64) — метод Latent Semantic Analysis, не требующий внешних моделей.
- Базовая проверка retrieval показала hit@5 = 1.000, recall@5 = 1.000, MRR@5 = 0.781 на 12 контрольных запросах.
- После добавления 3 новых документов (threading/multiprocessing, NumPy, Pandas) retrieval стал корректно возвращать фрагменты по новым темам.
- Mini-RAG сработал корректно для запросов, покрытых базой знаний; на запросах вне базы возвращал нерелевантные фрагменты.

## 3. База знаний и подготовка документов

- Предметная область: язык программирования Python (основные концепции и стандартная библиотека).
- Источник документов: собственные текстовые описания (20 документов), встроены в ноутбук.
- Число исходных документов: 20 (до обновления), 23 (после обновления).
- Число чанков после разбиения: 83 (до обновления), 95 (после обновления).
- Какой способ чанкинга использовался: фиксированное разбиение по символам с перекрытием.
- Основные параметры чанкинга: chunk_size=200, overlap=50.
- Комментарий: база знаний по Python хорошо подходит для retrieval, потому что каждый документ посвящён конкретной теме (списки, словари, ООП, декораторы и т.д.), что позволяет однозначно сопоставить запрос с ожидаемым документом. Документы достаточно содержательны (400-650 символов), чтобы после чанкинга каждый фрагмент нёс полезную информацию. При этом тематическая близость документов создаёт интересные случаи для retrieval — например, запрос про декораторы может вернуть фрагменты из документов про функции или ООП.

## 4. Retrieval и индекс

### 4.1. Эмбеддинги и индекс

- Какая embedding-модель или способ векторизации использовались: TF-IDF (max_features=5000, sublinear_tf, ngram_range=(1,2)) + TruncatedSVD (n_components=64).
- Какая метрика сходства использовалась: cosine similarity (через inner product после L2-нормализации).
- Какой индекс `FAISS` использовался: IndexFlatIP (точный поиск по inner product).
- Какой `top_k` использовался по умолчанию: 5.
- Что показали первые примеры retrieval: запросы по конкретным темам (словари, декораторы, файлы, тесты) возвращали чанки из ожидаемых документов на первых позициях.

### 4.2. Контрольные запросы и оценка retrieval

- Сколько контрольных запросов использовалось: 12.
- Что считалось релевантным ответом: наличие хотя бы одного чанка из ожидаемого документа в top-5.
- Какие метрики retrieval считались: hit@5, recall@5, MRR@5.
- Итоговый `hit@k`: 1.000
- Итоговый `recall@k`: 1.000
- Дополнительные метрики (если были): MRR@5 = 0.781.
- Какие запросы оказались самыми простыми: запросы с уникальными терминами (defaultdict, asyncio, logging, permutations) — ожидаемый документ на 1 месте.
- Какие запросы оказались самыми проблемными: запросы с общими терминами (например, «наследование классов» или «добавить элемент в список») — правильный документ в top-5, но не всегда на 1 месте (MRR < 1).

## 5. Эксперимент по параметрам retrieval и обновление базы знаний

- Какой параметр сравнивался: chunk_size.
- Какие два варианта сравнивались: chunk_size=200 (overlap=50, 83 чанка) vs chunk_size=400 (overlap=100, 43 чанка).
- Как изменилось качество retrieval: hit@5 остался 1.000 для обоих вариантов; MRR@5 вырос с 0.781 до 0.889 при chunk_size=400.
- Какой вариант вы выбрали как основной и почему: chunk_size=200 оставлен как основной, поскольку более мелкие чанки лучше подходят для mini-RAG (контекст точнее), хотя chunk_size=400 показал чуть лучший MRR.
- Что именно было обновлено в базе знаний: добавлены 3 новых документа — «Многопоточность и multiprocessing» (doc_21), «NumPy — основы» (doc_22), «Pandas — основы» (doc_23).
- Как была выполнена переиндексация: полный пересчёт чанков, перестроение TF-IDF + SVD, создание нового индекса FAISS.
- Что изменилось в retrieval после обновления базы знаний: запросы про GIL стали возвращать doc_21 вместо doc_16; запросы про NumPy и Pandas стали возвращать новые документы doc_22 и doc_23 на первых местах.

## 6. Mini-RAG и результаты

Ссылки на файлы в репозитории:

- Оценка retrieval: `./artifacts/retrieval_eval.csv`
- Примеры ответов mini-RAG: `./artifacts/rag_examples.csv`
- Сравнение до/после обновления: `./artifacts/retrieval_before_after_update.csv`

Короткая сводка:

- Контекст формировался из top-3 релевантных чанков, объединённых через разделитель.
- Для генерации ответа использовался шаблонный подход: лучший чанк оформлялся в ответ с указанием уровня релевантности (по score).
- Источники (doc_id, название документа, номер чанка) возвращались вместе с ответом.
- Лучше всего mini-RAG сработал на вопросах с уникальными терминами: «Как обрабатывать исключения?», «Что такое генератор и yield?», «Как использовать регулярные выражения?».
- Хуже всего — на вопросах вне базы знаний («Как подключиться к PostgreSQL?», «Как развернуть приложение на сервере?»): retrieval возвращал нерелевантные фрагменты.
- Качество retrieval напрямую определяло качество итогового ответа: если нужный фрагмент попадал в top-3, ответ был по делу; если нет — ответ был нерелевантным.

## 7. Анализ

База знаний по Python оказалась удачным выбором для учебного pipeline: документы достаточно разнообразны по лексике, чтобы TF-IDF мог различать темы, и достаточно содержательны для формулирования конкретных вопросов. Чанкинг с chunk_size=200 давал фрагменты, каждый из которых содержал 1-2 смысловых факта, что хорошо для точного retrieval. При этом эксперимент показал, что chunk_size=400 давал чуть лучший MRR (0.889 vs 0.781), вероятно потому что более крупные чанки содержат больше ключевых слов и точнее сопоставляются с запросами.

Формальная оценка retrieval (hit@k, recall@k, MRR@k) оказалась очень полезной: она показала, что все 12 контрольных запросов покрыты (hit=1.0), но часть из них возвращает правильный документ не на первом месте (MRR < 1). Это важно для RAG, где контекст формируется из top-k фрагментов.

Обновление базы знаний наглядно показало, как добавление новых документов меняет результаты поиска. Запросы про GIL, NumPy и Pandas стали возвращать релевантные новые документы. При этом переиндексация с TF-IDF + SVD требовала полного пересчёта словаря и матрицы, что для production-сценария было бы ограничением.

Наиболее показательные ошибки mini-RAG связаны с запросами вне базы знаний (PostgreSQL, деплой) — система возвращала «ближайшие» фрагменты, которые были нерелевантны. Это основное ограничение: шаблонный генератор не может определить, что контекст не отвечает на вопрос. Использование LLM для генерации позволило бы добавить фильтрацию по релевантности.

## 8. Итоговый вывод

Для учебной retrieval-задачи оптимальный базовый конвейер: TF-IDF + SVD для эмбеддингов, FAISS IndexFlatIP для поиска, chunk_size в диапазоне 200-400 символов с перекрытием. Этот подход не требует внешних моделей, работает быстро и даёт разумное качество на небольших базах знаний.

Главное, что я понял про качество retrieval: формальные метрики (hit@k, MRR@k) необходимы для отслеживания регрессий и сравнения параметров; без них невозможно объективно оценить, улучшает ли изменение конфигурации реальное качество поиска.

Связь retrieval и mini-RAG прямая: если retrieval не находит нужный фрагмент, никакой генератор ответа не компенсирует это. Качество retrieval — это потолок качества RAG.
